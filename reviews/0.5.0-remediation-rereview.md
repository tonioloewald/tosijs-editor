## BLOCKERS — must be fixed before tagging

### B-A · Under change tracking, caret Backspace and Delete work exactly once, then are dead keys forever

`src/tosijs-styled-editor.ts:188` · correctness · **confirmed by probe**

`<p>hello world</p>`, `trackChanges = true`, caret at the end. Backspace #1 correctly gives `hello worl<tosi-del>d</tosi-del><caret>`; presses #2–#5 leave `doc.innerHTML` byte-identical and `changes.length === 1`. Delete from offset 0 is the same: one `<tosi-del>h</tosi-del>`, then nothing. Untracked, the same four presses delete four characters.

`deletableFilter` rejects only `.sel-start`/`.sel-end` and empty text, so `previousLeafNode`/`nextLeafNode` keep returning the character already inside the just-created `<tosi-del>`. That node is length 1, so `backspace()` takes the else branch, `topSingleParentAncestor` climbs to the `<tosi-del>`, and `removeNode → trackDeletion` hits `if (el?.closest(DEL_TAG)) continue` (`closest` matches self) yet still returns `true`, so the caller also skips its own removal. Net no-op; the caret never advances past the mark.

README's policy — "text already inside a `<tosi-del>` is left alone" — is right; the missing piece is that **nothing walks past** such a mark. Broader than first reported: a document opened with a pre-existing `<tosi-del>` (another author's, or your own round-tripped) is dead at that mark from the **first** Backspace. And when the adjacent mark holds multi-character text, `deleteEdgeCharacter` (:1028) does the `splitText` _before_ `trackDeletion` and ignores its return value, so the run is split inside the `<tosi-del>` and the deletion is still swallowed — the guard belongs in the navigation step, not only in `trackDeletion`.

Regression introduced by the remediation: at `d056f49` this path did an unconditional `top.parentNode?.removeChild(top)` (the original B3 untracked leak); `a0e2c43` turned the leak into a dead key. The existing test _"nothing leaves the document untracked on any delete gesture"_ (`src/tosijs-styled-editor.test.ts:1233`) presses Backspace twice and Delete once and asserts only that `textContent` is unchanged — which a no-op satisfies.

**Fix:** make `deletableFilter` (or the `previousLeafNode`/`nextLeafNode` call sites in `backspace`/`forwardDelete`, plus the two list and two table-cell equivalents) skip `DEL_TAG` subtrees while tracking, so the caret walks to the next live character. Regression test: three Backspaces under tracking → three distinct marks (or one extended mark) and a growing `changes.length`. **Re-review scope after the fix:** the same walk feeds list-item and table-cell deletion — re-check both.

### B-B · `acceptChanges()` deletes a block the user never deleted and destroys the caret with it

`src/tosijs-styled-editor.ts:1066` · correctness + blast-radius · **confirmed by probe (two independent shapes)**

Both reported shapes reproduce, from the ordinary gesture path (`markBounds()` + a real `keydown`):

- `<p>one</p><p>two</p>`, select the whole text of the **first** paragraph, Backspace → `<p><caret><tosi-del>one</tosi-del></p><p>two</p>` (correct). `acceptChanges()` → `<p>two</p>`, `insertionPoint() === null`.
- Same document, text of the **second** paragraph → after accept, `value === "<p>one</p>"`, one `<p>` left, `insertionPoint() === null`.

After accept, `focus()` does not recover; typing inserts nothing and every caret-based command (`insertTable`, `insertFootnote`, `setLink`) silently bails — the failure mode `insertionPoint()`'s own doc comment names. The untracked path on the same gesture gives `<p><caret></p><p>two</p>` and typing works, so accept-all fails to reproduce the result it owes.

Root cause: the `emptied` sweep **infers** block scope ("the `<tosi-del>`'s `parentElement` is a top-level block that is now empty"), which is equally true of an ordinary inline full-text deletion as of the block-scoped wrap it was written for. `trackDeletion`'s `asBlock` path records nothing to distinguish them. It then removes a block that still contains `.sel-end .caret` — the exact hazard `deleteSelection`'s own sweep (:2465) guards with `(!caret || !block.contains(caret))`.

Supporting (latent, not demonstrated): two emptiness predicates now exist and have already drifted — :1074 checks `img, hr, br, .editor-table` but not `DEL_TAG`; :2465 checks `DEL_TAG` but not the replaced-element set.

Regression introduced by the remediation: `git log -S"const emptied = targets"` → `a0e2c43`. At `d056f49`, `acceptChanges` was a bare loop and left `<p><caret></p>` intact.

**Fix:** record scope at creation — stamp `data-block-delete` on the `<tosi-del>` that `trackDeletion`'s `asBlock` path creates, and remove only blocks whose accepted deletion carries it. Independently, never remove a block containing `.caret`/`.sel-end` (reuse `deleteSelection`'s guard). Extract one shared `blockIsEmpty(block)` so the two predicates cannot drift further. Tests for both shapes (block-selected vs text-selected) asserting surviving block count **and** that `insertionPoint()` is non-null. The neighbouring test at `:1263` pins the intended whole-block case, so a scope-stamping fix is cleanly distinguishable from it and needs no weakening of that assertion.

### B-C · `openInsertion` escaping an enclosing `<tosi-ins>` relocates typed and pasted text out of the word being edited

`src/tosijs-styled-editor.ts:934-935` · correctness + blast-radius · **confirmed by probe**

`<p>A<tosi-ins data-author="sam" data-session="other">QUICKBROWN</tosi-ins>Z</p>`, caret between `QUICK` and `BROWN`, one `X` → `AQUICKBROWNXZ` (expected `AQUICKXBROWNZ`). The same DOM with `trackChanges = false` gives the correct `AQUICKXBROWNZ`, so the defect is specific to the tracked path.

`enclosing.after(ins)` correctly avoids nesting but places the new mark after the **whole** enclosing insertion; `enterInsertion` then does `ins.appendChild(ip)`, dragging the caret out of the word, and `contentKey` inserts before the relocated caret. Also measured:

- **Paste/drop** takes the same target (:3108) and is worse — `insertTransfer(null, 'PASTED')` mid-insertion lands the text after the enclosing mark while the caret stays mid-word.
- **Your own earlier session** hits it too: `currentInsertion()` matches on author **and** session, so reopening a saved tracked document and typing inside your own earlier insertion misplaces text identically. README (~:371) explicitly blesses that gesture, and `src/changes.ts` (~:62) states the design intent — "a reviewer needs to be able to put the caret in a proposed sentence and adjust it before accepting". That is exactly the gesture that breaks.

Nothing downstream repairs it: `normalize()`, undo, `acceptChanges` and `rejectChanges` all operate on text that has physically moved. The remediation's own test _"an insertion is never nested inside another insertion"_ (`src/tosijs-styled-editor.test.ts:1133`) types `ab` first, so the caret sits at the **end** of the enclosing mark, where escaping and nesting look identical — the suite stays green.

Honest qualification: for a human typist the misplacement is visible immediately (green-underlined character appears in the wrong place). It is silent for paste/drop and for programmatic or LLM-driven edits.

**Fix:** split the enclosing insertion at the caret — clone its attributes (id, author, session, time) onto a tail `<tosi-ins>` for the text after the caret and open the new mark between the halves. Non-nested and positionally honest. Test with the caret mid-word inside another author's `<tosi-ins>` asserting `textContent === 'start apXYproved end'`, not merely the absence of nesting; add the paste variant.

### B-D · Table "Delete Row" / "Delete Column" bypass change tracking entirely

`src/commands.ts:634` and `:668` · blast-radius · **confirmed by running the shipping code**

`trackChanges = true`, caret in a cell of `<ul class="editor-table"><li>a1</li><li>b1</li><li>SECRET</li><li>b2</li></ul>`, then `doCommand('deleteTableRow')` (a default menubar item, `src/toolbar.ts:412-413`): the row's prose is gone from `parts.doc` and from `editor.value`, `editor.changes.length === 0`, and `rejectChanges()` cannot bring it back. `deleteTableCol` is identical. Both are bare `for (const c of rowCells) c.remove()` loops that never touch tracking.

`git diff d056f49..HEAD -- src/commands.ts` shows the remediation never touched either command, while the sibling table-cell **keyboard** paths (`:2945`, `:2970`) were converted to `removeNode`/`deleteEdgeCharacter`. The B3 sweep covered keydown handlers and stopped at the command registry — so the comment added at `src/tosijs-styled-editor.ts:1010-1016` ("EVERY destructive path goes through this") and `README.md:358-362` ("every deletion wraps in `<tosi-del>` … inside a table cell. Nothing leaves the document without a mark and an entry in `changes`") are both **false as shipped**. README's "Not implemented" list discloses only line-break tracking.

The propagation half is worse than the two commands: the fix landed on the component's **private** `removeNode`, and `EditableContext` (`src/commands.ts:36-53`) exposes no tracking hook at all — so every host-authored command added through the documented extension point (`editor.commands.myCommand = fn`, EXTENSIBILITY.md:36) inherits the same hole by construction, and each author re-discovers it alone. The project's own standard, visible in `refusesStructuralDelete`, is to **refuse** rather than silently restructure without a record; these two commands silently restructure and record nothing.

**Fix:** add a tracked-removal member to `EditableContext` (`removeNode(node: Node): void`, wired by `getContext()` to the component's `removeNode`), route `deleteTableRow`/`deleteTableCol` through it, and document it in EXTENSIBILITY.md as _the_ way a custom command deletes. One regression test per table command asserting `changes.length === 1` and that `rejectChanges()` restores the cells. Until fixed, the README/CHANGELOG "every deletion" / "nothing leaves the document" claims **must** be narrowed. **Re-review scope after the fix:** correctness + blast-radius over the remediation diff only.

### B-E · `Selectable.withoutBounds` silently destroys the caret when its block holds no text node — a host calling `checkSpelling()` gets a dead editor

`src/selection.ts:861` · blast-radius · **confirmed by probe (real keyboard events)**

`doc.innerHTML = '<p>one</p><p>ab</p>'`, caret at the end of `ab`, two real Backspace keydowns → `<p><span class="sel-end caret"></span></p>` (the empty-block sweep deliberately keeps the block holding the caret, `:2461`). Then `await el.checkSpelling()` → document is `<p>one</p><p></p>`, `.sel-end` is gone, `insertionPoint()` is `null`. Typing `qq` inserts nothing; ArrowLeft and Enter are no-ops. Identical typing worked before the check.

`createBounds()` (`:732`) is two bare `<span>`s with no text node, so a caret in a textless block leaves the block with zero text nodes. `withoutBounds` saves `offset = 0`, removes the markers, runs `fn`, then calls `textIndexOf(block).locate(offset)`; with no text nodes `parts` is empty and `locate` returns `null` (`:373-380`), and the `finally` block's `if (!pos) continue` abandons the detached marker permanently.

Reachability is routine, not exotic: (a) backspacing the last character of a paragraph, as above; (b) the mousedown handler's empty-element branch (`:553-558`) appends bare bounds into any clicked empty element; (c) `connectedCallback` appends the initial bounds to the first block (`:1350`), so a host whose initial `value` is `<p></p>` starts in the fatal state and the **first** `checkSpelling()` kills it. `checkSpelling()` is the host-invoked entry point the README tells integrators to call — on blur, on a timer, before submit — so this fires inside the host's app and reads as "the editor stopped accepting input".

Related quieter symptom, same root cause: a caret in an **empty table cell** is not lost but _moved_ — after `checkSpelling()` the markers come back inside the _first_ cell, because `topLevelAncestor` resolves to the table rather than the cell and the offset is the table's whole-text index.

The second reported mechanism (a marker that is a direct child of `parts.doc`, where `topLevelAncestor` returns the already-disconnected marker and `if (!block?.isConnected) continue` skips it) is structurally real but no path was found that produces it — treat it as hardening, not as a demonstrated bug.

**Fix:** make the restore total. When `locate()` returns `null`, fall back to appending the marker to its block (or to a next-sibling position captured alongside the offset); treat a marker whose `topLevelAncestor` is itself as already top-level and re-insert into `root`. A `finally` whose job is to put view state back must have no path that drops it. Tests: caret in an empty block, caret in an empty table cell, caret as a direct child of the doc.

## MAJORS — fix now or file as scheduled follow-ups (do not silently defer)

### M-1 · One delete gesture mints N unrelated change ids

`src/tosijs-styled-editor.ts:2443` · correctness · **confirmed by probe**

`changeId()` (`src/changes.ts:56`) mints per call; `trackDeletion` (`:951-954`) hoists `const id = changeId()` above its loop precisely so a batch shares one id; `removeNode` (`:1017-1019`) calls `trackDeletion([node])` one node at a time. The remediation replaced `this.trackDeletion(nodes.map(topSingleParentAncestor))` (present at `d056f49:2273`) with a per-node `removeNode` loop, so the batch id is gone.

Measured: a three-paragraph selection delete yields 3 marks with 3 distinct ids — minted **out of document order** (the interior block gets `-0` before the first paragraph's `-1`), so a UI sorting by id misorders rows. Worse and far more common: a _single_ paragraph `<p>the <b>quick</b> brown</p>` fully selected fragments into 3 ids; `acceptChanges(middleId)` then leaves `"the  brown"` (doubled space) and `rejectChanges()` cannot restore it — a document neither party proposed, reachable entirely through the documented `acceptChanges(id)` API.

This is the stack's own stated contract, not an appeal to prior art: README (`:342`) warns that finer granularity turns a rewritten sentence "into confetti", `restampPastedChanges` deliberately mints one id for all pasted marks, and `src/tosijs-styled-editor.test.ts:1398` pins it. The paste path upholds the contract; delete and cut now break it. With tracking on nothing is lost (`rejectChanges()` with no argument still restores everything), which is why this is major and not blocker.

**Fix:** thread an optional gesture id through `removeNode`/`deleteEdgeCharacter` into `trackDeletion`, minted once in `deleteSelection` and shared with its interior-block loop and empty-block sweep. Test: `new Set(changes.map(c => c.id)).size === 1` after one multi-block tracked delete, and after one fully-selected mixed-inline paragraph.

### M-2 · The `deleteSelection()` false-return fix was applied only under `trackChanges`, so the default path still lies — and eats an extra character

`src/tosijs-styled-editor.ts:2425` · correctness · **confirmed by probe, twice (API level and through the real keydown handler)**

The interior-block loop reads `this.removeNode(block); if (this.trackChanges) wasAnythingDeleted = true`. The comment the remediation added at `:2413-2417` describes exactly the defect that remains in the **default** mode.

Three paragraphs, markers on exact block boundaries so `selectedLeafNodes()` is empty after the interior block is removed:

- `trackChanges = false` → removes `<p>two</p>`, merges p1 into p3, **returns `false`**.
- `trackChanges = true` → same gesture returns `true`.

End-to-end with real keydowns, untracked: Backspace → `<p>on<caret>three</p>` (the `e` eaten on top of the intended deletion); Delete → `<p>one<caret>hree</p>` (the `t` eaten). The fall-through at `:2933` re-enters `backspace()`, which re-calls `deleteSelection()`, finds nothing (`unmark()` ran, so the re-`markBounds()` at `:2489` is a no-op) and deletes a character.

`deleteSelection()` is public and documented as "return true if something was deleted"; seven call sites branch on it, including the table-cell Backspace/Delete pair (`:2934`/`:2959`). Verified **pre-existing**, not a remediation regression — `git log -L 2405,2450` shows the prior code was a bare `block.remove()` that also set nothing. The shape needs an exact block-boundary selection across 3+ blocks; the near-miss cases (partial selection at either end, two-block selections, select-all) all correctly return `true`.

**Fix:** set `wasAnythingDeleted = true` unconditionally when an interior block is removed; add the untracked case to the test that currently covers only the tracked one (`:1213`, `:1244` both set `trackChanges = true`).

### M-3 · The structural-delete refusal is silent at runtime — every host enabling `trackChanges` ships a dead keystroke with no hook to explain it

`src/tosijs-styled-editor.ts:1047` · blast-radius · **confirmed by code read**

`refusesStructuralDelete` is `return this.trackChanges`. Three paths return bare and silent (`removeListItem :1932`, `backspace :2330-2336`, `forwardDelete :2376-2382`), two more silently skip the merge (`listForwardDelete :2008`, `deleteSelection :2478`). The keystroke is genuinely dead: `preventDefault()` runs unconditionally at `:2933`/`:2958` **before** dispatch, and since no `updateUndo` runs there is no snapshot and no `internals.setFormValue` either.

No signal exists at any layer — `dispatchEvent` appears twice in `src` (`selection.ts:711` `selectionchanged`, plus one inside a doc comment), and there is no console output. That is inconsistent with this codebase's own convention: `commands.ts:331`, `:726`, `:745` all complain when refusing. This is the one refusal that says nothing. No test exercises any refusal path either.

Refusing is the right policy and README `:389-397` / CHANGELOG `:48-50` document it clearly — for the **integrator**. The person who feels it is the end user, who gets a key that does nothing. One overstatement in the original finding: a host _can_ render a static "paragraph merges are disabled while tracking" note today, since it sets `trackChanges` itself; what is impossible without a component change is contextual feedback at the moment of the dead keypress.

Soft end of major: opt-in, off by default, no data-loss risk (refusing is the safe behaviour), fix is purely additive. Need not block the tag.

**Fix:** dispatch a bubbling, composed `CustomEvent('change-refused', { detail: { reason: 'line-break-tracking' } })` from `parts.doc` at each refusal point, plus a dev-mode `console.warn` matching the `setLink` precedent; document it next to `trackChanges` and in the properties table.

## MINORS AND NITS

### m-1 · `restampPastedChanges` gives every pasted mark the SAME id _(unverified)_

`src/tosijs-styled-editor.ts:3154` · correctness · **not independently verified** — the code read confirms `const id = changeId()` is minted once outside the loop and written to every `<tosi-ins>` and `<tosi-del>` in the fragment.

Copy a tracked revision — `<tosi-del>old</tosi-del><tosi-ins>new</tosi-ins>` — from one tracked document into another: both marks carry one id, so `acceptChanges(id)` accepts the deletion _and_ the replacement insertion, which is verbatim the failure `changeId()`'s own doc comment says the sequence counter exists to prevent.

**Triage caveat — do not apply the recommendation as written.** The finding's fix (call `changeId()` per mark inside the loop) directly contradicts the documented and tested paste contract that M-1 relies on: README `:342` and `src/tosijs-styled-editor.test.ts:1398` require a paste to be **one** change. The real kernel is narrower: a pasted **del+ins pair** should be two ids (or one id plus a grouping attribute), while a pasted run of same-kind marks should stay one. Resolve M-1 and m-1 together, and state the grouping rule in one place.

### m-2 · The local `IconElement` alias is unnecessary, and the upstream issue justifying it is filed on a false premise

`src/toolbar.ts:77` · blast-radius · **confirmed; severity adjusted major → minor during verification**

The premise in the code comment and in `UPSTREAM.md` — "`exports` only publishes `./icons`" — is false. tosijs-ui 1.15.0's exports map has a `"./*"` wildcard (`./dist/*.d.ts` / `./dist/*.js`), `dist/icon-types.d.ts` exports `IconElement`, and `import type { IconElement } from 'tosijs-ui/icon-types'` type-checks under this repo's exact tsconfig (`--traceResolution`: _Using 'exports' subpath './\*' with target './dist/icon-types.d.ts'_; a negative test errors `TS2322`, proving it is not silently `any`).

The valid kernel is different from what was filed: `import type { IconElement } from 'tosijs-ui'` and `from 'tosijs-ui/icons'` both give `TS2305`, so "not re-exported from any **named** entry point" is true — "no way to name the type" is not. Issue #176 needs re-scoping, not closing.

Downstream cost is real and confirmed against the built artifact: `dist/toolbar.d.ts:28-29` ships `type IconElement = ...` (non-exported) inside the exported `commandButton` signature, with the false comment shipped verbatim, so a consumer cannot name the type to cast around a future widening.

**Constraint the finding missed:** `peerDependencies` is `"tosijs-ui": "^1.13.0"`, and `IconElement` does not exist in 1.13.0 (it appears in 1.14.x). Importing the type therefore also requires raising the peer floor to `^1.14.0`. The zero-risk half — write `export type IconElement` so consumers can name it, and correct the ledger row and the comment — costs nothing and should land regardless.
