## Blockers (must fix before tag)

### B-1 — `openInsertion`'s split silently destroys a tail with no text content
`src/tosijs-styled-editor.ts:963` · correctness + blast-radius · **verified, reproduced twice**

```
if (tail.textContent) ins.after(tail)
```

`tail.appendChild(after.extractContents())` has already **moved** every node after the caret out of the enclosing `<tosi-ins>`. A tail holding only replaced/void content has `textContent === ''`, so it is never re-attached and the nodes are dropped on the floor — no `<tosi-del>`, no entry in `changes`, no error. Confirmed for `<img>`, `<br>` and `<hr>` tails; a text-only control round-trips correctly, isolating the cause to the gate rather than the split arithmetic.

Reachability is ordinary, and **does not need a second author or a reload**: `insertTransfer` calls `openInsertion()` unconditionally, and `commands.insertImage` does `ip.before(image)` with `ip` inside a live insertion. Verified single-session repro: type `ab` → `insertImage` → ArrowLeft → paste → the image is gone. The foreign-mark path (`currentInsertion()` requires both `data-author` *and* `data-session` to match) makes your own insertion split-eligible on the next session — documented behaviour, so one keystroke in front of a saved image destroys it.

The propagation point is sharp: **the same commit** (`cf89bf5`) added `blockIsEmpty()` at `src/dom-utils.ts:428` with the doc comment *"'No text' is not enough on its own: an image, a rule, a line break or a table is content with no text content … Two copies of this test existed and had already drifted"* — and then made exactly that mistake 460 lines away. The helper leaked its leverage on its first opportunity.

**Fix:** `if (tail.firstChild) ins.after(tail)` — node presence, not text presence, is the predicate the adjacent comment ("there is no tail") actually describes. Add regression tests for an `<img>` tail and a `<br>` tail. Then grep for other "is this empty" tests that should route through `blockIsEmpty`.
**Re-review scope:** correctness + blast radius over the remediation diff only — every caller (typing via `enterInsertion`, paste/drop via `insertTransfer`) shares this path.

### B-2 — README and CHANGELOG promise `structural-edit-refused` + `preventDefault()` for Delete Row / Delete Column; both refuse silently, and there is no seam for a host command to fire it
`src/commands.ts:636` and `:673` · correctness + blast-radius · **verified, reproduced**

`README.md:396-413` enumerates five refusals — the three keystroke block-merges **and** Delete Row / Delete Column — then states without qualification that *"A refusal fires a cancelable `structural-edit-refused` event carrying `detail.reason` … show a note, or call `preventDefault()` on it to allow the edit."* `CHANGELOG.md:44-54` repeats it. Both files are in `package.json` `files`, so both ship in the tarball. **Two of four documented refusal reasons never fire**, and `preventDefault()` cannot reach the table path because nothing cancelable is dispatched.

`deleteTableRow` and `deleteTableCol` refuse with a bare `if (ctx.tracksChanges()) return` — no event, no `console.error` (which `commands.ts` *does* use when declining at lines 80, 353, 757, 776, making these two the outliers). Runtime probe with tracking on and a caret in a cell: a listener that also calls `preventDefault()` recorded `events seen: []` for both commands.

Both are live items in the **default** menubar (`src/toolbar.ts:412-413`) with no disabled state — `grep trackChanges src/toolbar.ts` returns nothing. So with `trackChanges = true`, Table ▸ Delete Row from the shipped UI produces no DOM change and no signal at any layer: precisely the dead affordance M-3 was written to eliminate, now on the two refusals a user is *most* likely to notice, since a menu click has no "maybe nothing was meant to happen" reading.

The propagation half is the repeat: `refuseStructural()` is **private** on the component (`tosijs-styled-editor.ts:1144`), and `EditableContext` gained `removeNode()`/`tracksChanges()` but no way to refuse audibly — so `EXTENSIBILITY.md:82-88` ("**Restructuring?** Check `ctx.tracksChanges()` and **decline**") instructs every host-authored command to reproduce the hole by construction. That is the identical shape `EXTENSIBILITY.md:67-75` records for the *previous* round. Commit order confirms it: `cf89bf5` added the table refusals; the very next commit `88a9f88` added `refuseStructural`, the event, and the README paragraph naming those two commands — without wiring them.

Existing test `src/tosijs-styled-editor.test.ts:1445` asserts only `toContain('SECRET')`, which a dead command satisfies exactly as well as a signalled refusal — the same weakness that file itself calls out at ~1357 about the original B3 test.

**Fix, preferred:** add `refuseStructural(reason: string): boolean` to `EditableContext`, delegating to the component's method; call it from both table commands; document it in EXTENSIBILITY.md next to the `removeNode`/`tracksChanges` rule. Apply the same treatment to `listForwardDelete` (`tosijs-styled-editor.ts:2128`), which has the identical silent shape and no doc coverage.
**Minimum acceptable:** amend `README.md:405` and `CHANGELOG.md:52` to state the two table refusals are silent. Do not ship a README promising an event the shipped default menubar does not fire.
**Re-review scope:** seam fix → correctness + blast-radius over the remediation diff (the `EditableContext` shape change touches every construction site). Docs-only path → Tier 0.

Note for the decision: the *editing behaviour* here is safe — content is preserved and refusal is the intended outcome. What is broken is the advertised notification and override.

## Majors — fix now if B-1/B-2 are being touched anyway, else file

### M-1 — the documented `preventDefault()` override produces a half-applied edit
`src/tosijs-styled-editor.ts:2454` (and `:2501`, `:2050`) · correctness · **verified, reproduced**

Take the README at its word. Doc `<p>one</p><p>two</p>`, caret at the start of the second paragraph, tracking on, a listener calling `preventDefault()`, Backspace →

```
<p>on<tosi-del data-change=…>e</tosi-del><caret>two</p>     changes: [{kind:'delete', text:'e'}]
```

Two independent failures collide. (1) The merge itself — `caretBlock.remove()` at `:2477` — is a raw DOM removal that never goes through `removeNode()`/`trackDeletion`, so the paragraph break vanishes with **nothing in `changes`**: exactly the failure `refusesStructuralDelete` exists to prevent, now reachable through a documented API. (2) The character that rides along is *marked* rather than removed, so the document is simultaneously mid-merge and mid-proposal. `rejectChanges()` → `onetwo`; accept → `ontwo`; the original was `one` / `two`. Neither resolution is a document either party proposed.

Controls: tracking off gives `<p>on<caret>two</p>` (the extra-character-on-merge is pre-existing and independent); tracking on with no listener refuses correctly. What is new is the override making them collide. `grep preventDefault src/tosijs-styled-editor.test.ts` finds it only in a comment.

**Fix:** decide what the override means and make the code mean it. Simplest honest option — when refusal is overridden, perform the merge as a plain **untracked** structural edit (skip `deleteEdgeCharacter`/`removeNode` on that branch entirely) and document that overriding produces an untracked structural change. Alternative: drop `preventDefault()` from the README and make the event non-cancelable (notification only), defensible since there is no structural mark to record the result in. Either way, test Backspace-with-listener asserting final document **and** `changes`.

### M-2 — `restampPastedChanges` does not clear `data-block-delete`
`src/tosijs-styled-editor.ts:3283` · correctness + blast-radius · **verified, reproduced, incl. a no-hand-editing path**

`restampPastedChanges` exists to strip authority foreign markup asserts about itself; it rewrites `data-change`, `data-author`, `data-author-name`, `data-session`, `data-time`. B-B added a sixth attribute that changes what a mark *means* — `data-block-delete` (stamped at `:1034`, read at `:1180`) — and restamp does not touch it. kilpi is an attribute **blocklist** (`FORBIDDEN_ATTRIBUTES = {"ping"}`, `on*`, unsafe URL schemes), so `data-*` survives paste, drop and `value` verbatim.

Verified: paste `<tosi-del data-change="x" data-author="sam" data-block-delete="">struck</tosi-del>` into an empty paragraph with tracking off, move the caret elsewhere, `acceptChanges()` → the paragraph is removed (3 → 2). Same via the `value` setter. **No hand-crafted HTML is required**: a tracked whole-block delete in editor A serializes through `handleCopy` as `<tosi-del … data-block-delete="">two</tosi-del>`; ordinary copy → ordinary paste into editor B → `acceptChanges()` removes B's paragraph. Cross-editor paste of tracked documents is an advertised goal in `src/changes.ts`.

With `trackChanges = true` the paste is wrapped in `<tosi-ins>` and the `emptied` filter drops it, so the defect is specific to tracking-off paste, drop, and `value`. Blast radius is bounded by `blockIsEmpty` and the `.caret/.sel-end/.sel-start` guard — the loss is a structurally meaningful empty block, not arbitrary content — but it is silent, and no test in `src/*.test.ts` mentions `data-block-delete`.

**Fix:** `mark.removeAttribute('data-block-delete')` in the restamp loop — block scope is a property of a deletion *this editor performed*, not something inbound markup gets to assert, exactly as with the id and the attribution. Consider the same defence when parsing `value`. Document the attribute alongside the `<tosi-ins>`/`<tosi-del>` wire format in README's Tracked changes section (`CHANGELOG.md:106-111` already warns downstream consumers which change markup to preserve) — it is currently undocumented in README/CHANGELOG/SECURITY.md, and is the one attribute a downstream sanitizer is most likely to strip as noise, which would silently invert B-B's fix.
