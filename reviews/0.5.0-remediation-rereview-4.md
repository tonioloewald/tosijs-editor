## BLOCKERS (must fix before tag)

### B-1 — `blockIsEmpty`'s chrome skip treats every `.not-selectable` / `.do-not-spanify` subtree as nothing, so atomic widgets are silently destroyed at both call sites

`src/dom-utils.ts:477` · lens: correctness · **verified (adversarially confirmed)**

`el.closest('.not-selectable, .do-not-spanify')` matches the element **itself**, so any widget carrying the two classes `EXTENSIBILITY.md:133` tells plugin authors to use — "Atomic widgets should also carry `.not-selectable` / `.do-not-spanify`" — is invisible to the predicate, along with its whole subtree. This is a regression against the denylist it replaced.

Measured, HEAD vs. the denylist, component code otherwise untouched:

- **`deleteSelection` sweep (`tosijs-styled-editor.ts:2695`).** Doc `<p id=a>alpha beta</p><p id=b>gamma<span class="annotation do-not-spanify not-selectable not-editable"><span class="annotation-body"><img src=note.svg></span></span></p>` — exactly what the shipped `annotate` command builds (`src/commands.ts:536`). Select `al|pha beta` → `gamma|`, Backspace, tracking OFF (the default). OLD: annotation kept. HEAD: `doc.innerHTML === ''` — the annotation and its image are gone, with no mark, no row in `changes`, and no error.
- **`openInsertion` tail (`tosijs-styled-editor.ts:990`)**, at the very line whose comment says "the difference is always content". Caret after `quick` inside another author's `<tosi-ins>` followed by the same annotation, tracking ON, type X: `blockIsEmpty(tail)` is `true`, so the tail — which `extractContents()` has **already** moved out of the enclosing mark — is dropped unrecoverably. Same failure class the line was changed to fix, one widget kind over, and it loses content while tracking is on.
- `<tosi-footnote>` adds `not-selectable do-not-spanify` to itself in `connectedCallback` (`src/footnote.ts:57`), so a **connected** `<p><tosi-footnote></p>` measures `blockIsEmpty === true`. Not a regression (the denylist missed it too), but it is the headline case the allowlist was written to fix, and the skip cancels the fix for the one plugin shipped in this repo.

The skip buys nothing: `touchAffordances` is appended directly to `parts.doc` (`:1584`), a sibling of every block and never a descendant of one. The only chrome living _inside_ a block is the bounds markers, which the next line already handles and which are `<span>`, already in `INLINE_WRAPPERS`.

**Fix:** delete line 477. Line 478's marker check is the whole of the editor's in-block chrome. With 477 removed the suite is 277 pass / 1 fail, and the single failure is the assertion written to describe the bug (`blockIsEmpty(block('<div class="not-selectable"><img></div>'))` expecting `true`, `src/dom-utils.test.ts`) — invert it to `false`, which is what the predicate's own docstring demands ("must fail toward KEEPING things").

**Re-review scope:** correctness + blast-radius over the remediation diff only — both sweeps (`acceptChanges`' `emptied` sweep ~`:1251`, `deleteSelection`' sweep ~`:2695`) plus `openInsertion`'s tail gate.

### B-2 — the documented `preventDefault()` override on the new `merge-blocks-selection` refusal half-applies and corrupts the document; `rejectChanges()` no longer restores what the user had

`src/tosijs-styled-editor.ts:2711` · lenses: blast-radius + correctness (merged) · **verified (adversarially confirmed, both lenses independently)**

By the time `mayMerge` is evaluated, `deleteSelection` has already wrapped the selection in `<tosi-del>` via `removeNode(…, gesture)` (`:2645`, `:2671`) and pushed rows into `changes`. The merge that follows an override is a raw `lastBlock.insertBefore(...)` + `firstBlock.remove()` (`:2721-2726`) — **not** routed through `asUntracked`, unlike `backspace()`/`forwardDelete()` (`:2531-2540`, `:2590-2599`), which compute `overridden` before mutating and wrap the whole gesture precisely so this cannot happen.

Measured, tracking ON, host listener calling `e.preventDefault()` (the README's own recipe, `README.md:416-419`):

- Doc `<p>hello world</p><p>second para</p>`, select `world` → `sec`, Backspace →
  `<p><tosi-del>world</tosi-del><caret>hello <tosi-del>sec</tosi-del>ond para</p>`, one paragraph, `changes.length === 2` still pending.
- `rejectChanges()` → `<p>world hello second para</p>`: text back, but in one paragraph, in the wrong order, paragraph break gone with no record of who removed it. `acceptChanges()` → `<p>hello ond para</p>`. **Neither reproduces a document either party proposed.**

New in this diff: before it, the bare `!this.refusesStructuralDelete` made the merge unreachable under tracking, so nothing was dispatched and nothing was corrupted. It propagates because `README.md` (shipped in the npm tarball via `package.json` `files`) states as contract that `preventDefault()` "performs the edit untracked" for _all_ enumerated reasons, and this diff adds `merge-blocks-selection` to that list — so one global handler written to the documented contract now corrupts on the commonest gesture in the class (keydown routes both Backspace and Delete through `deleteSelection()` first). This is the **third** occurrence of the class `asUntracked` was introduced to prevent; the comment at `:1176` says so in as many words.

**Fix:** decide the refusal **before any mutation** — hoist the "this gesture will merge blocks" test to the top of `deleteSelection` (`blocks.length > 1` AND both ends will survive AND neither is `.editor-table`), and when the host overrides, run the whole of `deleteSelection` through `this.asUntracked(...)`, exactly as `backspace()`/`forwardDelete()` do; when refused, skip the merge as today. Fix M-2 (child-order reversal) in the same pass — the blocker's scrambled output is that bug, and the override path now reaches it. Add the missing override test at this site: after `preventDefault()` on a cross-paragraph selection Backspace, assert no `tosi-del`, `changes.length === 0`, and a document byte-identical to the `trackChanges = false` baseline.

**Re-review scope:** correctness + blast-radius over the remediation diff only — the hoist moves the refusal in front of the interior-block sweep and the leaf-node sweep, so re-check that `gesture` / `keptCaret` and `deleteSelection`'s return value are unchanged on the non-override tracked path, and that M-1's guard-folding did not change which gestures dispatch.
