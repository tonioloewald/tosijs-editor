## BLOCKER

### B‑1 — Mouse drag is no longer word-sticky by default, but the shipped README and the committed doc-site home page say it is, and the restoring knob is documented nowhere a consumer looks

`README.md:518` and `:520-530`; `CHANGELOG.md` `[Unreleased]`; `src/selection.ts:282`, `:570-575`, `:665` — **confirmed (both the docs and dx lenses, deduped; verified independently)**

At `v0.5.2` `extendSticky()` had no pointer gate, so a mouse drag snapped to word boundaries — the behaviour `CHANGELOG.md:132` announced as a 0.5.0 feature and that README still describes in two places (`| **Click-drag** | Selects words, sticky at boundaries |`, and the unqualified paragraph "**Click-drag is sticky at word boundaries.**"). At HEAD `stickySelection` defaults to `'touch'` and `stickyApplies` is `'always' || ('touch' && touchMode)` with `handleMouseDown` setting `touchMode = false`, so a mouse drag does not snap at all. The repo's own test pins the new behaviour (`src/selection.test.ts:708`, "by DEFAULT a mouse drag does not snap"), i.e. a passing test contradicts a README sentence.

Why it holds the tag rather than being a docs nit:

- README is in `package.json` `files` **and** is the doc-site home page (`docPaths: ['src','README.md']`); `docs/index.html:508`/`:511` carry the stale text verbatim in the committed web root.
- The escape hatch is invisible: `stickySelection` is absent from README's Component API table, absent from the Mouse-selection section, absent from `CHANGELOG.md [Unreleased]` (which has only `### Added` and `### Fixed`), and absent from the generated site — `grep stickySelection docs/` finds only the unrelated export `stickySelectionBounds`. Its only prose is a private `/** */` JSDoc at `src/tosijs-styled-editor.ts:947-969`, which reaches `dist/*.d.ts` and nothing a reader sees.
- So a 0.5.2 host loses an announced feature silently, reads docs that say it still works, and files it as a regression instead of setting `editor.stickySelection = 'always'`.

The per-pointer design itself is not disputed — it is well argued in `1646226` and in the JSDoc. Only the documentation shipping beside it is wrong.

**Fix (docs only, no code):**
1. `README.md:518` — change the row to state the per-pointer rule (fingertip snaps; mouse keeps character precision) and qualify the paragraph at `:520-530` the same way.
2. `README.md:758` Component API table — add a `stickySelection` row (`'touch' | 'always' | 'never'`, default `'touch'`), noting `'always'` restores 0.5.2's mouse behaviour and that it is a live property, settable at any time.
3. `CHANGELOG.md [Unreleased]` — add a `### Changed` heading naming the default change and the new property; this is the only upgrade signal a 0.5.2 consumer who relied on sticky mouse drags will get.
4. Rebuild `docs/` so the home page stops asserting it.

**RE-REVIEW SCOPE: Tier 0 only** if the remediation is documentation (README + CHANGELOG + API table + rebuilt `docs/`). If the *default* is changed in code instead, re-review correctness + blast-radius over the remediation diff.

With `<h1 id="title">Chapter One</h1><p>Some prose</p>` and a mid-heading→mid-paragraph selection: untracked Backspace yields `<p class="">Chapter prose</p>` (heading and its `id` gone); tracked + accept yields `<h1 id="title">Chapter prose</h1>`; the untracked *keystroke* path yields `<h1 id="title">…</h1>`. `runDeleteSelection`'s raw branch (`:3273-3280`) merges into `lastBlock`; `mergeBlocksRaw` (`:3017`), `trackStructuralEdit` (`:1521`, via `blockLike`) and both list-item loops (`:2557`, `:2634`) keep the earlier block.
