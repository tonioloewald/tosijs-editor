## BLOCKERS

### B‑1 — Untracked Backspace/Delete across a block boundary EATS a character of the neighbouring block (NEW; found in triage, not by any lens)

`src/tosijs-styled-editor.ts:3005` (and the mirror at `:3059`)

With `trackChanges` **off** — the shipped default (`:945`) — the character deletion on the untracked path runs *unconditionally*, with no `crossesBlocks` guard, and the block merge happens after it:

```ts
if (node.nodeType === 3 && (node.textContent || '').length > 1) {
  this.deleteEdgeCharacter(node as Text, 'end')   // deletes the previous block's last char
} else { ... }
this.normalize()
// ...then merge the two blocks
```

Reproduced (happy-dom, HEAD, my own probe using the suite's own `press`/bounds helpers):

| fixture | gesture | result | expected |
| --- | --- | --- | --- |
| `<p>one</p><p>two</p>` | caret at start of `two`, **Backspace** | `<p>on⟨caret⟩two</p>` → **"ontwo"** | "onetwo" |
| `<p>one</p><p>two</p>` | caret at end of `one`, **Delete** | `<p>one⟨caret⟩wo</p>` → **"onewo"** | "onetwo" |
| same, `trackChanges = true` | Backspace, then accept | **"onetwo"** — correct | correct |

Three things make this more than a probe artifact: the tracked path returns *before* the character deletion and is correct on the identical DOM and identical caret placement; `insertionPoint()`/`deletionTarget()` are pure DOM traversal, so the path is layout-independent and happy-dom is adequate evidence here; and **the source says so itself** — `backspace()`'s own comment records "with the check on the merge alone the character deletion ran first, so a refused merge still ate a character of the neighbouring block, unbounded, with no event to observe." That was fixed for the *refused* case by hoisting `refuseIfUnmergeable`. The *allowed* untracked merge still eats the character.

**Pre-existing, not a regression of this diff** — the untracked merge body is byte-identical in `89e2336` (checked against `git show 89e2336:src/tosijs-styled-editor.ts`). It blocks the tag anyway: it is silent content loss on the default path with the commonest keystroke in a text editor, it is a two-line fix, we now have a repro, and the code is under active change in this very diff. No test covers it — the only untracked merge tests (`UNTRACKED <key> at a <label> boundary destroys nothing`, `src/tosijs-styled-editor.test.ts:1904`) exercise the *refusal*, which returns before this body.

**Fix:** gate the character deletion on `!crossesBlocks` on both paths — a cross-block gesture deletes a paragraph break, not a character, which is the rule the comment above it already states. Do it inside the extracted `mergeBlocksRaw` from M‑3 so it lands once, not twice. Add a test asserting `<p>one</p><p>two</p>` + untracked Backspace === `onetwo`, and the Delete mirror. Confirm once in a live browser via `bun start` before closing.

### B‑2 — Accepting a tracked block merge permanently strips every descendant `id`, silently and undocumented

`src/tosijs-styled-editor.ts:1408` (lens: correctness + blast-radius, deduped)

`resolvedClone`'s new unconditional strip removes `id` from every element in the cloned content; `trackStructuralEdit` then strikes the originals, and `acceptChanges` removes them — so the only copies that still held the ids leave the document. Reproduced in triage:

- `<p id="intro">Alpha <a id="figref" href="#x">link</a></p><p>Beta.</p>`, tracked Backspace, `acceptChanges()` → `<p id="intro">Alpha <a href="#x">link</a>…Beta.</p>`; `#figref` count **0**, in the document and in `value`.
- `rejectChanges()` instead → `#figref` survives. An **untracked** merge on the same fixture keeps both ids. So turning tracking on silently destroys identity that tracking off preserves, and 0.5.x refused cross-block merges outright, so there was nothing to lose before.

Blast radius: in-document `href="#figref"`, `aria-labelledby`/`aria-describedby`, `label[for]` are left in place pointing at nothing — the document is internally *inconsistent*, not merely plainer, with no DOM or a11y error anywhere. Reached from three gestures (`:3000`, `:3054`, `:3233`). In-session undo restores it, but `value`/`internals.setFormValue` have already been written id-less and the undo stack does not survive a reload. Nothing in CHANGELOG or README says ids are dropped.

**This is why the cycle flag is set.** The strip was added in `ef326cc` ("Fix the two 0.6.0 blockers: footnote corruption"), i.e. it IS the B‑1 remediation of the previous review. And it is a one-third-applied fix: `reviews/0.6.0-structural-tracking-r2.md:153` prescribed three parts — strip in `blockLike`, strip in `resolvedClone`, and "transfer the id in `acceptChanges`' `emptied` sweep so it lives on exactly one element at all times." Only the middle one landed. The skipped part is exactly what keeps accept lossless.

**Fix:** park identity rather than deleting it — `data-tosi-id` on the clone, restored when the `data-block-insert` mark is accepted/unwrapped (reject already discards the clone). Must be fixed **together with M‑1**: simply stripping the block's own id too would make `#intro` vanish from the *accepted* document, trading one loss for another. One identity decision for the whole proposal lifecycle, at one address. Then add a test over **accept**, not only over the pending state, and state the chosen behaviour in CHANGELOG.

### M‑1 — The merged proposal keeps the first block's own `id`, so the pending document and `value` carry duplicate ids
`src/tosijs-styled-editor.ts:1432` / `:1514` (lens: blast-radius + correctness, deduped — reported separately as major and minor; keeping major)

`resolvedClone` builds its fragment from `block.childNodes` only, so its `[id]` sweep can never reach the block element; `blockLike` does `cloneNode(false)`, which carries every attribute including `id`. Reproduced: `<p id="intro">Alpha.</p><p>Beta.</p>` + tracked Backspace → `querySelectorAll('#intro').length === 2`, `value` contains `id="intro"` twice, and `querySelector('#intro')` returns the **struck** copy by document order — so a TOC link or a host's scroll-to-anchor lands in deleted text, and a mid-review save persists invalid DOM. Self-healing on resolution, but the review window is exactly when pending documents get stored. The guarding test `ids stay unique — two anchor targets for one href is invalid DOM` (`src/tosijs-styled-editor.test.ts:2614`) uses a fixture with no `id` on either block, so it passes while both halves are open. Same fix pass as B‑2; extend that fixture to carry an id on the first block **and** on a descendant.

### M‑2 — Rejecting a chain of tracked merges leaves a stray empty paragraph in the document and in `value`
`src/tosijs-styled-editor.ts:1632` (and the mirror sweep at `:1596`) (lens: correctness)

Reproduced: `<p>Alpha.</p><p>Beta.</p><p>Gamma.</p>`, two tracked Backspaces, then `rejectChanges()` → **4 paragraphs**, `<p></p>` present verbatim in `value`. Rejecting in reverse id order is correct, so the defect is purely the order `this.changes` yields. Root cause: the `proposed` sweep snapshots `c.element.parentElement` and keeps it only if `parentNode === this.parts.doc`; for an intermediate proposal the `data-block-insert` mark's parent is the wrapping `<tosi-del>`, so its `<p>` is excluded from the removal sweep, and `rejectChange` later unwraps the `<tosi-del>` leaving it empty. One stray block per intermediate step.

Pre-existing in the base, but **this diff's CHANGELOG rewrite is what makes that nested shape the documented contract** ("stays in the document as `<tosi-del data-block-delete>` wrapping the earlier `<tosi-ins data-block-insert>` … stays resurrectable by rejecting the later merge") — the diff promises a shape the resolution sweeps mishandle. Fix: derive the owning block with `this.block(c.element)` / `closest(BLOCK_SELECTOR)` in **both** sweeps (they are one predicate at two addresses and both miss a nested mark), or re-derive the sweep after the reject loop. The existing chain test (`:1996`) asserts only text presence, `changes.length === 0` and no `tosi-` in `value` — an extra empty `<p></p>` satisfies all three. Add a test that rejects a two-merge chain with no id and asserts the document is byte-identical to the original.

### M‑3 — The untracked block merge is still a mirrored twin in `backspace()` and `forwardDelete()`, on the default path
`src/tosijs-styled-editor.ts:3023` / `:3077` (lens: blast-radius + correctness/dryness, deduped — reported as major and as a nit; keeping major)

Fix: extract `mergeBlocksRaw(earlier, later)` with the guard inside it, drop the dead re-check (or say in the comment that it is belt-and-braces), and land B‑1's fix there.

### M‑4 — `renumberFootnotes`' duplicate-key repair silently deletes an authored note body (**verified in triage**, reported unverified)
`src/commands.ts:252` (lens: correctness)

Reported as an unverified minor; I probed it and it is real, so it is listed here:

- Placeholder with a trailing space: `<li data-footnote="k1">Footnote text </li><li data-footnote="k1">The real note</li>` → survivor is **`"Footnote text "`**. The authored note is deleted. The test is an exact `held.textContent === PLACEHOLDER` compare, so any whitespace decoration inverts the rule the code's own comment states ("never discard a note in favour of a placeholder, whatever the order").
- Both items authored: `First body` / `Second body` → survivor is **`"First body"`**; `Second body` is removed with no diagnostic and is unrecoverable from `value`.

`renumberFootnotes` runs on every `insertFootnote` and on resolution, so the loss happens on the next ordinary edit of an affected document — and documents saved by any pre-fix 0.6.0 build carry exactly the duplicate-key shape this repair was written for. Fix: compare `item.textContent?.trim()`, and when both items hold authored text do not delete — append the loser's text to the survivor or re-key it with a fresh `footnoteKey()`. Add both probes as tests.
