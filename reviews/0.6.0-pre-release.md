## BLOCKERS

### B‑1 — A tracked paragraph merge in a document containing a footnote permanently corrupts the footnote list, surviving both accept and reject

`src/tosijs-styled-editor.ts:1356` (`resolvedClone`) + `src/commands.ts:224` (`renumberFootnotes`) — **confirmed, re-reproduced at HEAD**

`resolvedClone` deep-clones a merged block's children and strips only `.sel-start/.sel-end/.caret`, `<tosi-del>` and `<tosi-ins>`. Nothing touches `data-footnote` or `id`, so a `<tosi-footnote data-footnote="k1">` inside a merged paragraph exists **twice** — once in the struck original, once in the `<tosi-ins data-block-insert>` proposal. The clone's `connectedCallback` schedules `renumberFootnotes`, which keys `existing` by `data-footnote` in a `Map` and does `existing.delete(key)` after the first ref — so the second ref with the same key finds nothing and mints `<li class="footnote" data-footnote="k1" id="k1">Footnote text</li>`.

Probe at HEAD (`<p>Alpha.</p><p>Beta.<tosi-footnote data-footnote="k1">…</tosi-footnote></p>` + a real note, `trackChanges = true`, caret at the start of the second paragraph, one real `keydown` Backspace, microtask flushed):

```
PENDING(accept)    lis=2  #k1=2  refnums=["1","2"]  [k1|k1|The important note] [k1|k1|Footnote text]
RESOLVED(accept)   lis=2  #k1=2  refnums=["1"]      [k1|k1|The important note] [k1|k1|Footnote text]
  value carries "Footnote text" placeholder: true
RENUMBERED(accept) lis=2  #k1=2  refnums=["1"]      ← explicit renumberFootnotes does NOT reap it
… identical residue after rejectChanges()
```

So: two `<li>` sharing one `data-footnote` **and** one `id` (invalid DOM, two `#k1` anchor targets), the note numbered 1 and 2 while pending, and a spurious placeholder that survives accept, reject and an explicit renumber — because `existing` is keyed by the colliding key and the Map's second `set` drops the real note out of `existing.values()`. The residue reaches `editor.value`, i.e. the form value and any saved document.

New in this diff: `v0.5.2` had no `resolvedClone`/`blockLike` and refused every cross-block merge while tracking, so nothing routinely cloned identity-bearing content. It is one Backspace away in the release's headline feature, and no test covers a merge over a footnote. Noted as an unverified follow-up in `reviews/0.6.0-structural-tracking-r2.md:176` and not fixed; this is the verified, worse version — the corruption survives resolution.

One sub-claim from the lens did **not** reproduce and should not go in the fix rationale: the author's real note text is never dropped. Both `<li>` persist; the placeholder merely wins the Map key.

**Fix:** make `renumberFootnotes` enforce one `<li>` per `data-footnote` — build `existing` from the first `<li>` per key, skip refs whose key was already placed in this pass, and remove duplicate-key items. That also repairs the same collision reachable by pasting a copied footnote. Additionally, `resolvedClone` should strip or re-key document-unique identity on the clone — at minimum drop `id`, since a block-scoped proposal currently duplicates every `id` in the block for as long as the merge is pending (r2 M‑2, still open). **Test:** Backspace-merge a paragraph holding a footnote, then assert exactly one `li.footnote` per `data-footnote` and no `Footnote text` placeholder after accept AND after reject — and confirm it goes red against unfixed code.

**Re-review scope:** correctness + blast-radius over the remediation diff only. The fix touches the footnote reconcile path, which also runs on undo, paste and drag.

### B‑2 — The shipped CHANGELOG documents the superseded-proposal rule the code deliberately reversed

`CHANGELOG.md:32-34` — **confirmed**

The 0.6.0 notes state: *"A chain of merges leaves no intermediate proposal behind — a superseded proposal is dropped rather than struck, because it never existed in the document anyone is reviewing and so must not be resurrectable."*

The code does the opposite, deliberately and with 12 lines of rationale: `src/tosijs-styled-editor.ts:1481` reads `// AN EARLIER PROPOSAL IS STRUCK LIKE ANY OTHER BLOCK.` and `:1496` is an unconditional `this.trackDeletion(blocksOut, id)`. A chained-merge probe leaves `<p><tosi-del … data-block-delete><tosi-ins … data-block-insert>Alpha.Beta.</tosi-ins></tosi-del></p>` in the document — one struck intermediate. The shipped test *"a chain of merges never orphans a change or loses text"* passes only because the intermediate IS struck.

Provenance: the sentence was written while absorption existed (`579846d`); `4522e37` removed absorption; `f5a4313` reversed drop→strike to fix r2's B‑1 text loss; `f89d962` corrected the identical sentence in `CLAUDE.md:324` and touched nothing else but `reviews/`. CHANGELOG was left behind.

Why this blocks a tag rather than being a docs nit: `CHANGELOG.md` is in `package.json` `files`, so it is the 0.6.0 release notes every npm consumer and every GitHub release page gets, for the release's headline feature. It misstates the DOM shape a host review UI must handle (`<tosi-del data-change=… data-block-delete>` is present and must be rendered), it misstates the review semantics (a superseded proposal **is** resurrectable — reject the later merge), and a host implementing the documented behaviour itself re-creates the r2 B‑1 bug that lost `Alpha.` and `Beta.` from a document with nothing pending. The project's own standard, from `f89d962`'s commit message: a doc asserting the opposite of the code is worse than silence, because it reads as settled.

Scope check: the claim is **not** in the generated `docs/` web root (`grep -rl` over `docs/` is empty) and **not** in README — exposure is the npm tarball, the repo, and release notes pasted from it.

**Fix:** rewrite the bullet to match the code and `CLAUDE.md:324-331` — a superseded proposal is struck like any other block (`data-block-delete`), because dropping it orphaned the earlier change once absorption was removed (an id with a delete half and no insert half). Note the consequence for `value` size across a chain, since the existing "the text is present twice" caveat understates it. Check the neighbouring claims in the same 25-line bullet against the code the same way while you are there.

**Re-review scope:** Tier 0 only — CHANGELOG wording, no code change.

### M‑1 — `merge-blocks-not-mergeable` ignores `preventDefault()` on both keystroke paths, and the only code that would honour it is unreachable under a comment saying the opposite

`src/tosijs-styled-editor.ts:2889`, `:2931`, `:2961` (and the twins at `:2985`, `:3003`, `:3033`) — **confirmed** *(merges two lens findings)*

`refuseIfUnmergeable` calls `this.refuseStructural(reason)`, **discards its return value**, and returns `true` unconditionally. `refuseStructural` returns `false` precisely when a host called `preventDefault()` — "I am overriding this refusal" — and that answer is thrown away. Probed: `<ul><li>one</li><li>two</li></ul><p>Beta.</p>`, caret at the start of `<p>`, a listener calling `preventDefault()`, Backspace, with `trackChanges` both off and on → one event fires, the document is byte-identical, `changes.length === 0`. A dead key with no second signal. `README.md:459-462` (new in this diff) lists this reason first and states in bold *"Calling `preventDefault()` performs the edit untracked"*.

Because `refuseIfUnmergeable` returns for exactly the predicate `crossesBlocks && !canMergeBlocks(pair)`, the inner branch at `:2931` (`if (!this.canMergeBlocks(pair)) { if (this.refuseStructural(…)) return; overridden = true }`) is **unreachable**, `overridden` is permanently `false`, `run` is permanently the identity function, `asUntracked` is never reached from a keystroke, and the third copy at `:2961` is always true when evaluated. That dead branch is the only site on these paths that reads `refuseStructural`'s return — so a reader checking "is the override honoured?" finds code that honours it and never learns it cannot run. `asUntracked`'s own doc comment at `:1494` describes exactly this keystroke case, which is evidence the override was meant to be honoured here and is now shadowed by the guard added to fix r2's B‑2.

Compounding it, the three paths disagree about one reason code. The selection path at `:3076` **does** read the return and routes through `asUntracked(() => runDeleteSelection(blocks, 'raw'))` — probed with a selection spanning `<ul>` and `<p>`: without the override, 3 tracked deletions; with it, `changes.length === 0`, `one`/`two`/`Beta.` gone raw, and the merge still does not happen because `runDeleteSelection`'s own `canMergeBlocks` re-rejects the pair. So that path loses tracking of deletions tracking could represent and still does not perform the structural edit the override was invoked to allow — the exact "half-applied gesture" shape the surrounding comments say had to be fixed three times.

Finally, the comment at `:2906-2912` still reads *"there is no mark for that — so refuse. A host that overrides the refusal gets the edit UNTRACKED"*, immediately above the new comment saying merges are now recorded. Filed as M‑9 in three prior reviews (`reviews/0.6.0-structural-tracking-r2.md:196`), still unfixed.

**Fix — decide the contract and make all three sites agree.** Recommended: this refusal is about **valid DOM, not review policy** (it fires with tracking off, where "untracked" is meaningless), so make it non-overridable — fire a non-cancelable event or a distinct reason, and amend README to exclude `merge-blocks-not-mergeable` from the `preventDefault()` promise explicitly. If it stays overridable, `refuseIfUnmergeable` must `return this.refuseStructural(reason)` and the selection path must not drop tracking of the parts it can track. Either way: collapse to **one guard per gesture** (delete the dead inner `canMergeBlocks` branch, the `overridden`/`run` machinery, and the now-redundant check inside `run()`), delete the stale comment in both twins, and add tests for Backspace, Delete and a cross-block selection, with and without `preventDefault()` — the only existing override test (`src/tosijs-styled-editor.test.ts:1683`) uses `deleteTableRow`. Do not leave two 70-line copies each carrying a dead branch; r2 already asked for `mergeBlocksTracked(earlier, later)`.

### M‑2 — `editor.stickySelection` is a write-once snapshot, and its own doc comment promises otherwise

`src/tosijs-styled-editor.ts:961` — **confirmed, re-reproduced at HEAD**

The field reaches the `Selectable` at exactly one place: `:1892` in `connectedCallback`. There is no getter/setter, no `onPropChange`, no attribute reflection; `stickyApplies` reads only the Selectable's own copy. The JSDoc at `:959` says *"Assigned straight through to the `Selectable`, so it can be changed at any time and takes effect on the next drag."*

```
post-connect set: component= always   selectable= touch   ← inert, silent
via creator:      component= never    selectable= never   ← works
via attribute:    component= touch    selectable= touch   ← sticky-selection="never" does nothing at all
```

So a host building the obvious "snap selection to words" preference toggle ships a dead control, and the markup form is inert too. This is the only knob a host has over the mouse-drag behaviour change this release makes (see F‑4 below). Gate 2 fires: every test sets `Selectable.stickySelection` directly (`src/selection.test.ts:703, 726, 761, 775`); nothing crosses the component seam, so deleting line 1892 outright leaves the suite green. The default literal `'touch'` is also written twice (`:961` and `src/selection.ts:282`) with nothing tying them together.

**Fix:** make it a getter/setter forwarding to `this.selectable` when connected and holding a pending value before connect (and reflect the attribute, or drop the attribute claim), or delete the field and document `editor.selectable.stickySelection` as the knob. Remove the duplicated default. Add a component-level test that sets it **after** connection and asserts a mouse drag snaps.

### M‑3 — The only layout-capable WebKit lane sits outside every automatic gate, and the new attestation gate is vacuous

`package.json:45` (no `releaseDoctor` key) — **confirmed** *(merges the security and blast-radius findings)*

`test:browser` is new in this diff, and release-doctor runs every `test`/`test:*` script it finds. `package.json` has **no `releaseDoctor` block at all** and there is no `release-attestation.json`, so:

- `publish.yml`'s new *"Attested lanes need an attestation"* step — added in this very diff, citing practices #1751 — resolves `LANES=""`, prints "no attested lanes declared", and passes. The gate is a no-op for this repo.
- Since `63a78b9` ("test:browser brings up its own dev server") the CI colour flips but the hole does not: the wrapper starts `bun bin/site.ts` first, tosijs-ui's `ensureDevCerts()` `process.exit(1)`s because `tls/*` is gitignored and absent on a runner, and the wrapper's message matches **no** `CANNOT_RUN` pattern — so on the tag CI gets a **hard Tier 0 FAIL explained by a TLS-cert message**, not by anything about the release. Silently green became loudly red for the wrong reason.
- Locally the lane passes and produces exactly the Arabic deltas `CLAUDE.md` records (0.00px for whole-word marks; 1.00px on 3/98 glyphs for a one-character mid-word mark). A `beforeAll` failure also reports as `(fail) (unnamed)` — the unnameable-failure/cry-wolf shape release-doctor's own comments exist to prevent.

Net: the only lane in the repo with layout — the one that measured the numbers this release is built on — runs in no release path, and nothing in `package.json` says so.

**Fix (pick one before tagging):** declare `releaseDoctor.attestedLanes: ["test:browser"]` and run `tools/attest.ts` so the tag carries an attestation covering this tree (then both gates do real work); **or** declare `releaseDoctor.advisoryLanes: { "test:browser": "<why>" }`, which still runs the lane and downgrades a failure to WARN, preserving the local signal; **or**, if CI is meant to run it, add `playwright install --with-deps webkit` plus a cert path / `RTL_URL`. Separately, move the fixture setup inside a named test (or have `beforeAll` report a missing server as a stated precondition) so the failure is nameable. Already filed as virta #2891 (`kind:process`, `priority:high`, inbox), which asks for exactly this keep-decision — a filing, not a fix.
